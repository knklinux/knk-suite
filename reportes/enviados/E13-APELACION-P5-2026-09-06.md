## Por qué el VRT no encaja (argumento central)

El P5 elegido describe: *"Weak Login Function > Not Operational or Intended
Public Access"* — funciones de **login** que exponen acceso **público
pretendido**. El hallazgo no toca ninguna de las dos cosas:

1. **No es función de login.** El endpoint afectado
   (`POST /backend-api/files/upload_reservations`) es una API de subida de
   archivos autenticada, ajena al flujo de autenticación.
2. **No es acceso público pretendido.** Todo el flujo exige sesión válida
   (Bearer). Lo reportado es lo contrario de "público pretendido": una
   **capability firmada que el backend emite para un usuario y que cualquier
   principal (otro usuario autenticado o anónimo) puede ejecutar**.
3. **Hay impacto real de integridad, demostrado end-to-end:** el contenido
   escrito por la cuenta A se materializa en el archivo de la biblioteca de la
   cuenta B (verdad de fondo: B descarga su propio `content_url` y recibe
   `SYNTHETIC-A-INJECTED by account A`; captura incluida). El P5 es por
   definición "no explotable / acceso pretendido" — aquí hay explotación
   verificada y el acceso NO es pretendido por diseño.

## Categoría correcta propuesta

**Broken Access Control → Missing Function Level Access Control** (P4/P3 a
criterio del triager): el backend emite una firma SAS con claim `scid`
(client-id) que **no se valida en el momento de la escritura** — el control de
propiedad solo se aplica después, en el `claim_and_finish` (`user_mismatch`).
Ese es exactamente el patrón de control de acceso a nivel de función ausente.

## Texto listo para pegar en el hilo del submission

```
Hi team — thanks for the triage. I'd like to respectfully push back on the VRT
category, not the severity: P5 "Weak Login Function > Not Operational or
Intended Public Access" doesn't match this finding, because nothing here is a
login function or intended public access.

What I reported is an authenticated file-upload API that issues a signed
capability (Azure user-delegation SAS) carrying a scid (client-id) claim that
is never enforced at write time. The result, demonstrated end-to-end with two
self-owned accounts: a different authenticated account (and an unauthenticated
request) can overwrite the pending upload, and the victim's own claim flow
materializes the attacker's bytes in their library file — verified by the
victim downloading their own content_url and receiving the attacker's content
(screenshot + raw HTTP attached).

That is a missing object-level/functional access control on an authenticated
endpoint (Broken Access Control > Missing Function Level Access Control), not
an informational login issue. The ownership check only happens later, at
claim_and_finish (user_mismatch), which is what makes the write-time gap
exploitable within the ~5-minute SAS window.

If the team still assesses this as intended behavior after re-review, I'll
gladly accept the closure — happy to provide any additional evidence that
helps.
```
